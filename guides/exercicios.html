Prática orientada

Construa um histórico que você entende

Faça um checkpoint por vez no Git Bash (Windows) ou no terminal (Linux). Leia o resultado antes de avançar. Textos entre < e > são exemplos que você deve substituir. A publicação no GitHub é opcional.

Antes de começar: siga o guia de preparação e copie examples/site-da-turma para ~/oficina-git/site-da-turma. No Git Bash (Windows) e no terminal (Linux), ~ representa sua pasta pessoal. Trabalhe nessa cópia e confirme a pasta com pwd e ls. Se estiver em computador compartilhado, configure nome e e-mail somente neste repositório.

1. Inicie o repositório

Entre na cópia do projeto e crie a branch principal. O ponto final pede o status do repositório.

cd ~/oficina-git/site-da-turma
git init -b main
git status

Resultado esperado: o Git informa que você está na branch main, ainda sem commits, e lista os três arquivos como não rastreados.

Se não acontecer: use pwd e ls para localizar a cópia correta. Não execute git init na sua pasta pessoal inteira.

2. Registre a base do projeto

Prepare somente os arquivos do exemplo, confira a seleção e crie o primeiro snapshot.

git add index.html styles.css README.md
git status
git commit -m "Cria base do site da turma"
git log --oneline

Resultado esperado: o status mostra os três arquivos preparados antes do commit; depois, o log exibe um commit com a mensagem escolhida.

Se o Git pedir identidade: siga o guia de autoria, configure nome e e-mail e repita apenas o comando git commit.

3. Ignore rascunhos locais

Crie uma pasta rascunhos e um arquivo dentro dela pelo editor. Depois crie .gitignore com a linha rascunhos/.

git check-ignore rascunhos/notas.txt
git status
git add .gitignore
git commit -m "Ignora rascunhos locais"

Resultado esperado: check-ignore imprime o caminho do arquivo ignorado, e somente o arquivo .gitignore entra no novo commit.

Se o rascunho aparecer no status: confira se o arquivo se chama exatamente .gitignore e se contém rascunhos/ em uma linha própria.

4. Leia uma alteração antes de prepará-la

No editor, troque o texto visível do elemento <h1>, de Site da turma para Turma em construção, em index.html e salve.

git status --short
git diff -- index.html

Resultado esperado: o status marca index.html como modificado e o diff mostra a linha anterior removida e a nova linha acrescentada.

Se não houver diferença: salve o arquivo, confirme que editou a cópia versionada e procure o texto com seu editor antes de tentar novamente.

5. Observe o snapshot preparado

Prepare a primeira versão. Sem executar outro git add, mude o mesmo título para Turma colaborativa e salve novamente.

git add index.html
git diff --cached -- index.html
git diff -- index.html
git status --short

Resultado esperado: o primeiro diff contém Turma em construção; o segundo contém Turma colaborativa. O status mostra mudança preparada e mudança no trabalho.

Se os dois diffs forem iguais: você provavelmente executou git add depois da segunda edição. Continue, mas repita este checkpoint depois para observar os dois estados.

6. Faça commits pequenos e conscientes

Registre primeiro o snapshot já preparado. Em seguida, prepare e registre a edição que permaneceu na área de trabalho.

git commit -m "Atualiza título preparado"
git diff -- index.html
git add index.html
git commit -m "Conclui título colaborativo"
git log --oneline -3

Resultado esperado: são criados dois commits em sequência. O primeiro contém a versão preparada; o segundo registra a edição restante.

Se o segundo commit disser que não há mudanças: confira o conteúdo de index.html. Se a versão final já entrou no primeiro commit, apenas siga adiante.

7. Retire uma alteração do staging sem apagá-la

Edite uma frase já existente, salve e prepare o arquivo. Então retire-o do staging e confira os dois estados.

git add index.html
git diff --cached -- index.html
git restore --staged index.html
git status --short
git diff -- index.html

Resultado esperado: depois de git restore --staged, a edição continua no arquivo e aparece no diff comum, mas deixa de aparecer no diff preparado.

Se sua edição desaparecer: não salve outras mudanças. Use o histórico do editor ou peça ajuda; restore --staged sozinho não deveria alterar o arquivo de trabalho.

8. Desfaça um commit preservando o histórico

Prepare e registre a edição anterior. Com o status limpo, crie outro commit que desfaz somente esse último commit simples.

git add index.html
git commit -m "Testa uma nova frase"
git status
git revert --no-edit HEAD
git log --oneline -3

Resultado esperado: o log mantém o commit original e acrescenta um novo commit de reversão. O status volta a ficar limpo.

Se houver alterações antes do revert: pare e faça um commit ou guarde conscientemente seu trabalho. Não use reset --hard para limpar a atividade.

9. Crie e integre uma branch

Crie uma branch, acrescente uma descrição ao final de README.md, salve e faça o commit. Depois volte para main.

git switch -c melhoria-descricao
git add README.md
git commit -m "Melhora descrição do projeto"
git switch main
git merge --ff-only melhoria-descricao
git log --oneline --decorate -4

Resultado esperado: a branch main avança até o commit da melhoria por fast-forward; nenhum commit de merge adicional é criado.

Se o README não entrar no commit: confirme que salvou o arquivo. Se o merge recusar fast-forward, não force: consulte o diagnóstico.

10. Produza um conflito controlado

Com o status limpo, crie mensagem-alternativa. Nela, troque a frase do elemento mensagem por Aprendemos criando., salve e faça commit. Volte para main, troque a mesma frase por Aprendemos colaborando. e faça outro commit.

git switch -c mensagem-alternativa
git add index.html
git commit -m "Cria mensagem alternativa"
git switch main
git add index.html
git commit -m "Atualiza mensagem principal"
git merge mensagem-alternativa

Resultado esperado: o merge para com um conflito em index.html. O arquivo contém marcadores que delimitam as duas versões da mesma linha.

Se precisar recomeçar: execute git merge --abort enquanto o merge estiver em andamento. Isso retorna ao estado limpo anterior à tentativa.

11. Resolva e conclua o conflito

Abra index.html, leia os dois lados e deixe uma única frase: Aprendemos criando e colaborando.. Remova todos os marcadores, salve e abra a página no navegador.

git diff --check
git add index.html
git status
git commit -m "Combina as mensagens da turma"
git log --oneline --graph --decorate -6

Resultado esperado: git diff --check não aponta marcadores; o commit conclui o merge e o grafo preserva os dois caminhos anteriores.

Se o Git ainda indicar conflito: procure por <<<<<<<, ======= e >>>>>>>. Remova-os, salve e prepare o arquivo outra vez.

12. Conecte um repositório vazio

Opcional e com internet: crie no GitHub um repositório vazio, sem README, licença ou .gitignore. Substitua usuário e repositório no endereço.

git remote add origin https://github.com/<usuario>/<repositorio>.git
git remote -v
git push -u origin main

Resultado esperado: o remoto origin aparece para busca e envio; depois da autenticação, main passa a acompanhar origin/main.

Se o origin já existir: use git remote get-url origin e confirme o endereço. Não coloque senha ou token na URL; siga o gerenciador de credenciais.

13. Envie uma proposta em branch

Pessoa B: com autorização, clone o repositório em outra pasta, entre nela, crie uma branch e acrescente uma linha ao README. Use informações que aceite compartilhar.

git clone https://github.com/<usuario>/<repositorio>.git
cd <repositorio>
git switch -c melhoria-dupla
git add README.md
git commit -m "Propõe melhoria em dupla"
git push -u origin melhoria-dupla

Resultado esperado: a branch melhoria-dupla aparece no GitHub sem alterar diretamente a branch main.

Se houver erro de permissão: confirme a conta autenticada e o convite de colaboração. Sem acesso ou rede, faça a revisão e o merge localmente no mesmo computador.

14. Revise, integre e sincronize

No GitHub, Pessoa B abre um pull request de melhoria-dupla para main. Pessoa A lê o diff, conversa sobre a proposta e integra quando concordar. Depois cada pessoa atualiza sua cópia.

git switch main
git pull --ff-only
git log --oneline --graph --decorate -6
git status

Resultado esperado: a branch local avança para a versão integrada no GitHub, o log inclui a proposta e o status informa que não há alterações pendentes.

Se git pull --ff-only parar: não force nem apague commits. Execute git status e git log --oneline --all --graph e diagnostique a divergência com a turma.
